# Gateway Activity Event Model

This document describes the canonical backend event model for gateway runs.

The goal is to represent a run as a container for multiple concurrent activities instead of forcing all progress through one global `phase` or `status` field.

## Why This Exists

The old model worked for a single linear stream:

- model starts
- model thinks
- model types
- model finishes

That breaks once a run contains overlapping work:

- the assistant is streaming visible text
- reasoning is still in progress
- a tool starts and emits progress
- a subagent is spawned
- another agent contacts this agent mid-run

At that point there is no truthful single value like `thinking`, `typing`, or `tool_running` that describes the whole run.

The solution is:

- model the run lifecycle separately
- model each work unit as its own activity
- stream ordered events about those activities

## Design Principles

- A run is a container, not a global mutable phase machine.
- Every independently meaningful work unit gets its own `activityId`.
- Multiple activities may be active at the same time.
- Nesting is expressed with `parentActivityId`.
- Streaming content belongs on `activity.output`, not on generic status fields.
- Terminal state belongs on `run.completed` or `activity.completed`.
- UI labels like `typing`, `thinking`, or `waiting on agent` are derived projections, not canonical wire state.

## Event Families

The canonical backend event bus is a discriminated union centered on these event types:

- `run.started`
- `run.updated`
- `run.completed`
- `activity.started`
- `activity.updated`
- `activity.output`
- `activity.completed`

## Run Lifecycle

Run events describe the state of the turn as a whole.

- `run.started` means the run began
- `run.updated` means run-level metadata changed
- `run.completed` means the run ended with an outcome

Run events must not be used to say:

- the model is currently thinking
- the assistant is currently typing
- a tool is currently running

Those belong to activities.

### Run Outcomes

The run outcome answers only whether the whole run ended:

- `completed`
- `failed`
- `aborted`

## Activity Lifecycle

Activities describe concrete units of work inside a run.

Every activity has:

- `runId`
- `activityId`
- `kind`
- optional `parentActivityId`
- `rootRunId`
- `origin`
- optional `target`
- `ts`

Each activity progresses independently through:

- `activity.started`
- zero or more `activity.updated`
- zero or more `activity.output`
- `activity.completed`

### Activity Outcomes

Activity completion describes the result of that activity only:

- `completed`
- `failed`
- `cancelled`

One child activity failing does not automatically fail the whole run.

## Activity Kinds

The current model supports these canonical kinds:

- `assistant_message`
- `reasoning`
- `tool_call`
- `subagent_call`
- `peer_agent_call`
- `command`
- `file_change`
- `web_search`
- `compaction`

Additional kinds may be introduced later if they represent a real new work unit rather than a UI projection.

## Origin And Target

Every activity records where it came from. Cross-agent activities may also record where they are going.

### Origin

`origin` is a typed source descriptor:

- `user`
- `self`
- `subagent`
- `peer_agent`
- `system`

Typical examples:

- user message kicking off a run: `origin.type = "user"`
- assistant output generated by the current agent: `origin.type = "self"`
- nested work created because another agent contacted this agent: `origin.type = "peer_agent"`

### Target

`target` is optional routing metadata used for cross-agent work.

It may include:

- target `agentId`
- target `sessionKey`
- target `runId` when known

This lets the backend correlate outbound and inbound agent interactions without overloading one status field.

## Output Events

Streaming data belongs on `activity.output`.

Examples:

- assistant text deltas
- assistant accumulated visible text snapshots
- reasoning deltas or summaries
- command stdout and stderr chunks
- tool progress output when the tool emits streamable text

`activity.output` should not be used for terminal success or failure.

## Update Events

`activity.updated` is for non-terminal metadata changes, such as:

- a tool title becoming available
- partial tool result metadata
- a subagent moving from queued to running
- compaction indicating `willRetry: true`

If the payload is streamable user-facing content, it should be `activity.output` instead.

## Collaboration Semantics

The model is designed for both directions of agent collaboration.

### Outbound Collaboration

When this agent contacts another agent:

- emit a `subagent_call` or `peer_agent_call` activity
- attach agent metadata in `target`
- attach child progress under that activity when needed

Examples:

- spawning a child worker agent
- sending a message to another existing agent

### Inbound Collaboration

When another agent contacts this agent during a run:

- emit a first-class `peer_agent_call` activity representing the inbound contact
- set `origin.type = "peer_agent"`
- record the contacting agent in `origin`
- record the receiving agent in `target`
- attach all resulting local work as descendants of that inbound activity

That means any of these can become children of the inbound contact:

- `assistant_message`
- `reasoning`
- `tool_call`
- `subagent_call`

This is what makes simultaneous multi-agent interaction representable without collapsing state.

## Parent And Child Activities

`parentActivityId` expresses causality and nesting.

Examples:

- an assistant message may own a tool call
- a tool call may own a subagent call
- an inbound peer-agent call may own a local assistant reply

This gives the backend enough structure to support:

- tree views
- grouped timelines
- lane-based chat projections
- multiple concurrent typing indicators

## Example Event Flow

This is a representative sequence for a run that streams text, thinks, calls a tool, and talks to another agent:

```text
run.started
activity.started(kind=assistant_message, activityId=a1)
activity.started(kind=reasoning, activityId=r1, parentActivityId=a1)
activity.output(kind=reasoning, activityId=r1, delta="...")
activity.output(kind=assistant_message, activityId=a1, delta="...")
activity.started(kind=tool_call, activityId=t1, parentActivityId=a1)
activity.updated(kind=tool_call, activityId=t1, patch={ name: "read_file" })
activity.completed(kind=tool_call, activityId=t1, outcome="completed")
activity.started(kind=peer_agent_call, activityId=p1, parentActivityId=a1)
activity.updated(kind=peer_agent_call, activityId=p1, patch={ status: "running" })
activity.started(kind=assistant_message, activityId=a2, parentActivityId=p1)
activity.output(kind=assistant_message, activityId=a2, delta="...")
activity.completed(kind=assistant_message, activityId=a2, outcome="completed")
activity.completed(kind=peer_agent_call, activityId=p1, outcome="completed")
activity.completed(kind=reasoning, activityId=r1, outcome="completed")
activity.completed(kind=assistant_message, activityId=a1, outcome="completed")
run.completed
```

The important property is that several activities may be active simultaneously and truthfully.

## Derived UI State

The backend should not emit one global field like:

- `typing`
- `thinking`
- `tool_running`
- `waiting_on_agent`

Instead, UIs derive those labels from currently active activities.

Examples:

- if any active `assistant_message` has recent output, show typing
- if any active `reasoning` exists without visible text, show thinking
- if any active `tool_call` exists, show tool activity
- if any active `peer_agent_call` or `subagent_call` exists, show agent activity

For a group-chat-style UI, the same rule applies per actor or per lane.

That means the model supports:

- multiple agents typing to one agent at once
- one agent typing while another tool call is active
- inbound and outbound agent interactions overlapping in the same run

## Backend Responsibilities

Backend producers should emit canonical events directly rather than building ad hoc local shapes.

The backend source of truth should:

- emit one run lifecycle per run
- emit one activity per assistant message stream
- emit one activity per reasoning stream
- emit one activity per tool call
- emit one activity per outbound subagent or peer-agent interaction
- emit one activity per inbound peer-agent interaction

Backend consumers should project from canonical events rather than inspecting free-form `phase` and `status` values.

Important consumers include:

- gateway chat and websocket projections
- OpenResponses streaming
- OpenAI-compatible streaming
- run snapshot builders
- logging and trace summaries

## Reducers And Snapshots

Some consumers need a current-state view instead of a raw event log.

Those consumers should build a reducer over canonical events rather than expecting the transport to carry precomputed snapshot state.

A reducer typically tracks:

- active runs
- activity tree by `activityId`
- current output buffers by activity
- completed outcomes
- latest metadata patches

This keeps the wire format simple and compositional.

## What This Model Replaces

This model replaces the idea that a run can be described by one free-form shape like:

- `stream: "assistant" | "tool" | "lifecycle"`
- `data.phase = "start" | "delta" | "thinking" | "typing" | "end"`
- `status = "started" | "completed" | "failed"`

That encoding forces unrelated concerns into one axis and becomes ambiguous as soon as concurrency appears.

The canonical event model solves that by separating:

- whole-run lifecycle
- per-activity lifecycle
- per-activity streamed output
- nested causality
- actor routing metadata

## Guidance For Future Changes

When adding new behavior, ask:

1. Is this a real unit of work with its own lifecycle?
2. Can it overlap with other work?
3. Would a user or system care about its identity independently?

If the answer is yes, it should probably be an activity.

When deciding between `activity.updated` and `activity.output`, ask:

1. Is this streamable content?
2. Would a transcript or live view render it as output?

If yes, use `activity.output`.

When deciding between run state and activity state, ask:

1. Does this describe the whole run ending or changing metadata?

If not, it probably belongs to an activity.
